# Map Calendar Reminders Package

Updated: 2026-08-03

Use this package for Map, Calendar, future Agenda Journey/Activity Session, Reminders, route/date/callback/follow-up boundaries, and trip/schedule handoff rules.

Current 4.2 reminder: Map-derived Calendar follow-ups should preserve explicit trip lineage (`sourceTripId`) when available, so confirmed schedule facts can become supporting context inside the originating shared-route memory.

Current map baseline: Map supports two versioned packs: `real-seoul-v1` for real-world Seoul and `cyber-wasteland-v1` for a faction-divided cyber wasteland. Seoul V1 includes 101 versioned read-only places spanning entertainment/media/company landmarks, civic/cultural/event destinations, beauty services, general and luxury shopping, supermarkets, a small convenience-store set, nightlife, general and plastic-surgery hospitals, four housing tiers, major transport hubs, parks, universities, landmark hotels, pharmacy districts, sports facilities, cinemas, bank headquarters, and public-safety institutions; addresses and coordinates are maintained as a dated local snapshot rather than live provider POIs. Geographic packs render through lazy-loaded MapLibre using the public OpenFreeMap Liberty style; fictional, imported, and failure-fallback packs render locally through `LocalMapCanvas`. One active world resolves to one recommended or explicitly bound map. Map Settings owns world binding, full player-pin creation/edit/delete management with arbitrary coordinate selection, local-image import, shared-image-service generation, visual presentation, and the per-world place-knowledge choice; the everyday Map owns search, place browsing/use, place details, trips, Footprints, lightweight pin visibility, and a clear link into that Settings manager without duplicating its creation form. Address/description text is recognition and search metadata, while required provider-neutral coordinates determine where a pin renders: geographic packs use latitude/longitude and fictional/custom packs use normalized canvas coordinates. Places separates catalog filtering from persisted map visibility: broad-category and individual-place eye controls change only rendered markers, while known-but-hidden records remain searchable, inspectable, and usable as trip destinations. `all_known` is the old-save-compatible default; optional `footprint_gated` mode withholds eligible authored nearby facilities from every catalog surface until a completed positioned journey reveals them. Mode changes retain discovery records, and manual role-position changes do not reveal places. Dense everyday categories default hidden. Search is a ranked current-world index over positioned known pack/player pins, with wrapped category controls, normalized multi-term matching, optional aliases/search terms, and bounded Latin typo tolerance; unmatched text remains an explicit free-form trip destination and never becomes an online POI request. Place taxonomy is shared across both renderers, search, place lists, details, and Settings: 14 broad groups provide concise browse/filter/visibility labels, while all 31 stable icon subtypes remain available in the new-place editor and continue to own persisted category values. Its idle state is map-first: search, a canonical role-position focus, an explicit arbitrary-point role-position action, and independent Journey, Places, and Footprints buttons remain visible; each opens a focused drawer. While traveling, the static coordinate control is relabeled as start-position focus, role-position reselection is locked, and a persistent primary journey card shows route, phase, progress, remaining time, ETA, and pending route updates. Coordinate placement remains exclusive in both renderers. The runtime uses no API key, device location, route planning, paid POI lookup, commercial map SDK, or provider-specific place identity. The old `/map/labs/kakao-compare` path is an inert compatibility redirect to `/map`. See `docs/product-decisions/LOCAL_NARRATIVE_MAP_PACKS.md`.

Approved Map Journey direction: Map remains the entry and source owner for known-destination journeys and later active area exploration. Transport is selected inside Map Journey planning; a separate Transit app is deferred until it has independent network utility. MJE-1 through MJE-4 are user-accepted and integrated locally: passive progress is now Footprints, Map Settings offers old-save-compatible all-known or Footprints-gated place knowledge per world, and completed positioned journeys can deterministically reveal nearby authored convenience stores and pharmacy districts. Event-based reveal, generated candidate places, active Exploration, and transit topology remain later stages. See `docs/architecture/MAP_JOURNEY_FOOTPRINTS_EXPLORATION_ARCHITECTURE.md` and roadmap 4.11.

Accepted Calendar/Agenda Journey direction: Calendar is the visible long-range confirmed-plan app; its current frontend is list-first and later CJA-1 may introduce Month/Week/Agenda views. A separate future `行程 / Agenda Journey` app owns today/near-term execution, while a hidden Schedule Orchestrator links confirmed Calendar commitments without taking ownership of Map Journey, Event Runtime, Activity Session, or downstream values. This direction is documentation-only under roadmap 4.12 and does not modify MJE code or authorize a route/store/timer/popup. See `docs/architecture/CALENDAR_AGENDA_JOURNEY_EVENT_ORCHESTRATION_ARCHITECTURE.md`.

Optional capability Pack reminder: Calendar may consume `reservation -> Calendar` world app context for labels, accents, and boundary presentation, including confirmed `reservation_board` nonstandard-app proposals, but Calendar still owns confirmed events, time editing, reminder promotion, relationship-fact review, and push scheduling. Map may consume `transit -> Map` world app context for title/context/boundary presentation, but Map still owns route, trip, location, ETA, shared-route facts, and Map-derived Calendar handoff.

Future Mini Scene reminder: Calendar and Map may each register a focused request Adapter under `docs/architecture/MINI_SCENE_MODULE_CONTRACT.md`. They keep confirmed-event/trip/location truth and decide request eligibility; they do not own world-profile selection, Book regex execution, artifacts, or text/HTML presenters.

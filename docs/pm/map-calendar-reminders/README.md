# Map Calendar Reminders Package

Updated: 2026-08-01

Use this package for Map, Calendar, future Agenda Journey/Activity Session, Reminders, route/date/callback/follow-up boundaries, and trip/schedule handoff rules.

Current 4.2 reminder: Map-derived Calendar follow-ups should preserve explicit trip lineage (`sourceTripId`) when available, so confirmed schedule facts can become supporting context inside the originating shared-route memory.

Current map baseline: Map supports two versioned packs: `real-seoul-v1` for real-world Seoul and `cyber-wasteland-v1` for a faction-divided cyber wasteland. Seoul V1 includes 101 versioned read-only places spanning entertainment/media/company landmarks, civic/cultural/event destinations, beauty services, general and luxury shopping, supermarkets, a small convenience-store set, nightlife, general and plastic-surgery hospitals, four housing tiers, major transport hubs, parks, universities, landmark hotels, pharmacy districts, sports facilities, cinemas, bank headquarters, and public-safety institutions; addresses and coordinates are maintained as a dated local snapshot rather than live provider POIs. Geographic packs render through lazy-loaded MapLibre using the public OpenFreeMap Liberty style; fictional, imported, and failure-fallback packs render locally through `LocalMapCanvas`. One active world resolves to one recommended or explicitly bound map. Map Settings owns world binding, detailed player-pin management, local-image import, shared-image-service generation, and visual presentation; the everyday Map surface owns search, place use, explicit pin creation, place details, trips, and lightweight pin visibility without draggable markers. Places separates catalog filtering from persisted map visibility: category and individual-place eye controls change only rendered markers, while hidden records remain searchable, inspectable, and usable as trip destinations. Dense everyday categories default hidden, and convenience stores also stay out of empty-search suggestions until the user searches or selects that category. Search is a ranked current-world index over positioned pack/player pins: empty focus exposes recent/diverse suggestions and categories, while normalized multi-term matching uses names, addresses, category semantics, optional aliases/search terms, and bounded Latin typo tolerance. New places inherit name/address/category search automatically; `aliases` are reserved for real alternate names and `searchTerms` for non-display discovery words. Selecting a result focuses its coordinate and opens its detail; unmatched text remains an explicit free-form trip destination and never becomes an online POI request. Player-pin category icon/tone semantics are shared across both renderers, search, place lists, details, and Settings, where a focused guide explains the six editable categories. Its idle state is map-first: search, a canonical role-position focus when the current map has one, and Places remain visible; add-place and the full Places-and-Pins manager are grouped inside Places. While traveling, the role-position control hides and a persistent primary journey card shows route, phase, progress, remaining time, ETA, and pending route updates; arrived journeys retain the same card for settlement. Trip detail and place-detail surfaces otherwise appear only after explicit user intent or active runtime state, and fictional faction legends start collapsed. Coordinate placement is an exclusive mode in both renderers, so existing markers cannot intercept a placement tap or replace an in-progress place draft. The runtime uses no API key, device location, route planning, paid POI lookup, commercial map SDK, or provider-specific place identity. The old `/map/labs/kakao-compare` path is an inert compatibility redirect to `/map`. See `docs/product-decisions/LOCAL_NARRATIVE_MAP_PACKS.md`.

Approved Map Journey direction: Map remains the entry and source owner for known-destination journeys and later active area exploration. Transport is selected inside Map Journey planning; a separate Transit app is deferred until it has independent network utility. The current passive Explore progression becomes the Footprints foundation, while active Exploration remains a later gated stage. MJE-1 transport-aware planning and MJE-2 Map-owned lifecycle/checkpoints are user-accepted and implemented in the current uncommitted tree without claiming an integrated commit. MJE-3's first low-impact, world-aware checkpoint Event Runtime adapter is implemented and remains `READY_FOR_USER_REVIEW`: only explicit in-route checkpoints are evaluated while Map is visible, Event Runtime owns eligibility/provenance/audit, and a pending update leaves the journey running until Map applies either no ETA change or a reviewed bounded two-minute delay. The primary map surface now keeps active journey status, progress, remaining time, and pending-update access visible. See `docs/architecture/MAP_JOURNEY_FOOTPRINTS_EXPLORATION_ARCHITECTURE.md` and roadmap 4.11.

Accepted Calendar/Agenda Journey direction: Calendar is the visible long-range confirmed-plan app; its current frontend is list-first and later CJA-1 may introduce Month/Week/Agenda views. A separate future `行程 / Agenda Journey` app owns today/near-term execution, while a hidden Schedule Orchestrator links confirmed Calendar commitments without taking ownership of Map Journey, Event Runtime, Activity Session, or downstream values. This direction is documentation-only under roadmap 4.12 and does not modify MJE code or authorize a route/store/timer/popup. See `docs/architecture/CALENDAR_AGENDA_JOURNEY_EVENT_ORCHESTRATION_ARCHITECTURE.md`.

Optional capability Pack reminder: Calendar may consume `reservation -> Calendar` world app context for labels, accents, and boundary presentation, including confirmed `reservation_board` nonstandard-app proposals, but Calendar still owns confirmed events, time editing, reminder promotion, relationship-fact review, and push scheduling. Map may consume `transit -> Map` world app context for title/context/boundary presentation, but Map still owns route, trip, location, ETA, shared-route facts, and Map-derived Calendar handoff.

Future Mini Scene reminder: Calendar and Map may each register a focused request Adapter under `docs/architecture/MINI_SCENE_MODULE_CONTRACT.md`. They keep confirmed-event/trip/location truth and decide request eligibility; they do not own world-profile selection, Book regex execution, artifacts, or text/HTML presenters.

# Map Calendar Reminders Package

Updated: 2026-08-19

Use this package for Map, Calendar, Agenda Journey, Activity Session, Reminders, route/date/callback/follow-up boundaries, and trip/schedule handoff rules.

Current 4.2 reminder: Map-derived Calendar follow-ups should preserve explicit trip lineage (`sourceTripId`) when available, so confirmed schedule facts can become supporting context inside the originating shared-route memory.

Current map baseline: Map supports two versioned packs: `real-seoul-v1` for real-world Seoul and `cyber-wasteland-v1` for a faction-divided cyber wasteland. Seoul V1 includes 106 versioned read-only places spanning entertainment/media/company landmarks, civic/cultural/event destinations, beauty services, general and luxury shopping, supermarkets, a small convenience-store set, nightlife, general and plastic-surgery hospitals, four housing tiers, major transport hubs, parks, universities, landmark hotels, pharmacy districts, sports facilities, cinemas, bank headquarters, public-safety institutions, and five reviewed real restaurant branches linked from Food Delivery by stable Map ID; addresses and coordinates are maintained as a dated local snapshot rather than live provider POIs. Geographic packs render through lazy-loaded MapLibre using the public OpenFreeMap Liberty style; fictional, imported, and failure-fallback packs render locally through `LocalMapCanvas`. One active world resolves to one recommended or explicitly bound map. Map Settings owns world binding, full player-pin creation/edit/delete management with arbitrary coordinate selection, local-image import, shared-image-service generation, visual presentation, and the per-world place-knowledge choice; the everyday Map owns search, place browsing/use, place details, trips, Footprints, lightweight pin visibility, and a clear link into that Settings manager without duplicating its creation form. Address/description text is recognition and search metadata, while required provider-neutral coordinates determine where a pin renders: geographic packs use latitude/longitude and fictional/custom packs use normalized canvas coordinates. Places separates catalog filtering from persisted map visibility: broad-category and individual-place eye controls change only rendered markers, while known-but-hidden records remain searchable, inspectable, and usable as trip destinations. `all_known` is the old-save-compatible default; optional `footprint_gated` mode withholds eligible authored nearby facilities from every catalog surface until a completed positioned journey reveals them. Mode changes retain discovery records, and manual role-position changes do not reveal places. Dense everyday categories default hidden. Search is a ranked current-world index over positioned known pack/player pins, with wrapped category controls, normalized multi-term matching, optional aliases/search terms, and bounded Latin typo tolerance; unmatched text remains an explicit free-form trip destination and never becomes an online POI request. Place taxonomy is shared across both renderers, search, place lists, details, and Settings: 14 broad groups provide concise browse/filter/visibility labels, while all 31 stable icon subtypes remain available in the new-place editor and continue to own persisted category values. Its idle state is map-first: search, a canonical role-position focus, an explicit arbitrary-point role-position action, and independent Journey, Places, and Footprints buttons remain visible; each opens a focused drawer. While traveling, the static coordinate control is relabeled as start-position focus, role-position reselection is locked, and a persistent primary journey card shows route, phase, progress, remaining time, ETA, and pending route updates. Coordinate placement remains exclusive in both renderers. The runtime uses no API key, device location, route planning, paid POI lookup, commercial map SDK, or provider-specific place identity. The old `/map/labs/kakao-compare` path is an inert compatibility redirect to `/map`. See `docs/product-decisions/LOCAL_NARRATIVE_MAP_PACKS.md`.

World Suite readiness note: `src/lib/map-world-suite-inspection.js` gives Map one read-only Catalog/native-identity/reference Interface, while `src/lib/production-map-world-suite-inspection-adapter.js` composes the real Map, Gallery, Event Runtime, and Chat owners without exposing their bodies. It reports built-in/user/Catalog identity, modification, Gallery linkage, player places, active/world binding, visibility, Footprints, current position/place session, active/history Journey use, persisted Event references, persisted Chat location-card references, and custom-pack capacity without changing Map. Catalog provenance and strictly normalized authored places survive trusted restore/save/reopen, `saveNow()` returns the real write receipt, and `mapStore.commitManagedMapPackMutation()` performs one managed create/update/delete with exact rollback. Gallery now has its own stable-folder/stable-asset Owner Adapter and hard-blocks ID/URL collision, referenced update/removal, or unsafe replacement; Map only consumes its asset ID. One typed Book/Gallery/Map Catalog and explicitly constructed product installation runtime install Gallery before Map, reverse that order on removal, and require successful System inventory persistence at every checkpoint. No built-in K-pop Catalog/manifest, startup caller, UI, activation, binding, relocation, or Journey mutation exists; the default standalone Map inspection still exposes only `owner + inspect`.

Landed event-card direction: EVE-2C adds Map V3 current-position provenance and durable place-session state, registers exactly one Map Event Surface host, and renders only the frozen interior production-arrival-briefing archetype. EVE-4B extends the owner boundary to Map V4 `deliveryJourneys`: Map owns courier route truth and reroute validation, while Food Delivery owns order/payment/conversation truth and Event Runtime stores only lineage. Manual relocation cannot forge journey arrival; explicit `Enter` is required before the local zero-token invitation and explicit expansion. Event Runtime retains proposal/log/instance/text truth, while Map validates anchors, session lineage, the three allowlisted no-mutation choices, card/pin layout, clustering/stacking, selection, layer coexistence, and return context. Stale/off-pack inputs fail closed, and projections remain derived rather than a second event record. This does not create an Event desktop app, place/discovery effects from coordinates, MJE-5 active exploration, Mini Scene runtime, Calendar/Agenda Journey, or CG generation.

Implemented place focus and entry: ordinary pin selection opens the concise Map-owned focus sheet, with `Go` or current-journey reuse while remote/traveling, explicit `Enter` at a coordinate-matched stable place, and contextual `Leave` while inside. Immediate relocation remains a sandbox action with `manual` evidence and no Journey record; completed travel records internally authorized `journey_arrival` evidence. The sheet has no permanent Event placeholder and shows an invitation only for an eligible inside session. Details, Share, and player-owned Manage preserve their existing ownership and progressive-disclosure behavior.

Active Map journeys now expose a small music/radio control beside the journey tools. It opens a focused Map-owned panel for the current trip while Music continues to own playback, playable-track resolution, queue/radio construction, credentials, local media, and the independent global floating player. Closing the Map panel leaves the Music floating player and playback untouched; leaving the active journey removes only the Map entry.

Place Details now owns a persisted `system` / Chinese / English / bilingual display preference. It changes SchatPhone-authored pin labels, search results, Places rows, and detail names/addresses without rewriting canonical place records, coordinates, search metadata, or existing journeys. Bilingual mode keeps map pins single-line while exposing a secondary name in browse surfaces and secondary name/address in Place Details. OpenFreeMap's own basemap labels remain controlled by its style and are outside this preference.

Current place-media baseline: `src/lib/map-place-media.js` keeps media separate from canonical place records and resolves one fixed `hero` presentation for every pack/player place. Grade `A` is an exact-place licensed photo, `B` is a clearly labeled real area view, `C` is an explicitly labeled generated reconstruction with generation provenance, and `D` is a non-evidentiary category fallback. The first reviewed pilot covers Gyeongbokgung, Seoul Station, Seoul Forest, SM Entertainment HQ, Starfield COEX Mall, Myeongdong Kyoja Main Store, Sillim-dong compact housing, and fictional Helix Spire. Seven real-photo WebP derivatives are byte/SHA-256-verified public project assets with author, source, license, alt text, and change disclosure; SM, Myeongdong Kyoja, and Sillim are deliberately `area_atmosphere`, while the fictional/user path uses `category_fallback`. Original candidates remain in a Git-ignored local source archive and are never runtime URLs. See `docs/design/MAP_PLACE_MEDIA_GOVERNANCE.md` and `docs/qa/MAP_PLACE_MEDIA_PILOT_2026-08-15.md`.

Current Chat-sharing note: a place detail can prepare a normalized Map-owned `location_share`, then hand recipient selection and explicit send to Chat. Cancel returns to the same place detail; opening a sent card restores that detail by stable `placeId`. Neither action changes current location, journey endpoints, trip progress, or Map source truth.

Approved Map Journey direction: Map remains the entry and source owner for known-destination journeys and later active area exploration. Transport is selected inside Map Journey planning; a separate Transit app is deferred until it has independent network utility. MJE-1 through MJE-4 remain integrated locally: passive progress is now Footprints, Map Settings offers old-save-compatible all-known or Footprints-gated place knowledge per world, and completed positioned journeys can deterministically reveal nearby authored convenience stores and pharmacy districts. The generic MJE-3 checkpoint adapter and compatibility UI remain covered behind an explicit test hook, but the production Map does not enable the temporary-route-obstruction trigger after product review found that it failed to name the affected actor, transport-specific action, and downstream schedule consequence. Ordinary no-event travel is the production baseline until a reviewed causal journey family is accepted. Event-based reveal, generated candidate places, active Exploration, and transit topology remain later stages. See `docs/architecture/MAP_JOURNEY_FOOTPRINTS_EXPLORATION_ARCHITECTURE.md` and roadmap 4.11.

Implemented Calendar/Agenda Journey direction: Calendar is the visible long-range confirmed-plan app. CJA-1 provides Month, Week, and Agenda views, selected-day and selected-event detail, all-day/multi-day/recurring projections, and complete manual event authoring over Calendar V3. CJA-2 adds the hidden persisted Schedule Orchestrator: one deterministic record per Calendar occurrence, idempotent materialization and required-deadline requests, stable Agenda Journey links, and startup/resume reconciliation. CJA-3 adds the separate `行程 / Agenda Journey` Home app and schema-V1 execution owner for today and the next 14 days. It consumes Calendar occurrence requests idempotently or accepts a manual plan, keeps travel and activity as distinct steps, records explicit completion/miss/skip/cancel state, and retains only stable evidence references to Map. CJA-4 adds the separate absolute-time Activity Session owner and restrained built-in Focus Companion. CJA-5 upgrades Activity Session storage to V2 and adds one midpoint-only Event Runtime family: `off` silently owner-validates keeping the current rhythm, while `text` stays inside Focus Companion and may request only a 0/2-minute timer adjustment. CJA-6A now documents the read-only Narrative Timeline contract and bounded AI-context seam; it adds no store, route, backup, or visible App. Activity Session completion still returns bounded evidence to Agenda Journey; no second Map clock, Gallery/Music read, HTML scene, or external owner mutation is introduced. See `docs/architecture/CALENDAR_AGENDA_JOURNEY_EVENT_ORCHESTRATION_ARCHITECTURE.md`.

Current Calendar implementation: Calendar storage V3 migrates V1/V2 and owns explicit start/end ranges, all-day state, recurrence, participation requirement, notes, reminder lead time, and an optional stable Map-owned `locationRef`; it never derives a destination from event title, prose, coordinates, or a “usual address.” The selected event detail shows current Map origin, selected transport estimate, recommended departure, predicted arrival, and predicted lateness for the selected occurrence. Changing role position or transport recomputes the projection without rewriting the appointment. Only explicit `Leave now` creates or reuses one Map-owned journey carrying the source Calendar event ID; another active journey blocks creation, and Map returns to the same Calendar context. This direct Calendar-to-Map path remains valid and does not manufacture an Agenda Journey step.

Current Agenda Journey implementation: `/agenda-journey` shows today, upcoming, in-progress, and finished plans; accepts bounded manual plans; and materializes Calendar occurrences through the CJA-2 request/acknowledgement seam. A location-bound plan derives current-origin ETA, predicted arrival, and leave-by guidance from Map, then starts or reuses one Map Journey only after explicit departure. Map arrival completes the travel step and unlocks the activity; the user must still explicitly start and complete or skip the activity. Required skips and unresolved required deadlines become missed, while cancellation preserves already completed travel evidence. Calendar source retirement and post-start fingerprint changes fail into retained reviewable state instead of rewriting executed history. Agenda Journey backup remains nested under the existing Calendar section, while Activity Session and Simulation persist independently and link by stable IDs. Automatic place entry, broader Agenda event families, media callers/richer companions, interactive HTML, and CJA-6B Narrative Timeline implementation remain later gates.

The accepted scheduling refinement keeps appointment start/duration/place in Calendar, derives recommended departure from the current Map position, creates one Map Journey only after explicit confirmation, and lets validated arrival unlock rather than complete the activity. Activity Session owns the later timer and completion policy. Its optional Focus Companion presentation may use timer presets and stable Gallery/Music/companion references, but optional events remain checkpoint collaborators and are never required for the base activity path.

Optional capability Pack reminder: Calendar may consume `reservation -> Calendar` world app context for labels, accents, and boundary presentation, including confirmed `reservation_board` nonstandard-app proposals, but Calendar still owns confirmed events, time editing, reminder promotion, relationship-fact review, and push scheduling. Map may consume `transit -> Map` world app context for title/context/boundary presentation, but Map still owns route, trip, location, ETA, shared-route facts, and Map-derived Calendar handoff.

Future Mini Scene reminder: Calendar and Map may each contribute source facts through a focused Event Runtime Adapter under `docs/architecture/MINI_SCENE_MODULE_CONTRACT.md`. They keep confirmed-event/trip/location truth and do not own scene authoring, world-profile selection, Book regex execution, artifacts, or text/HTML presenters.

# 任意世界观如何进入事件运行：难点与建议讨论稿

Updated: 2026-08-29

Status: `DISCUSSION_NOTE / NOT_A_CONTRACT / NOT_IMPLEMENTATION_AUTHORIZATION`

这份文档用于接续 2026-08-29 关于“用户换一套完全不同的文字世界观后，事件系统是否仍能工作”的讨论。它整理当前观察、主要难点、可供讨论的设计方向和验证建议。

它不是规则，不预先决定最终架构、字段、Store、产品流程或实施顺序，也不改变现有路线图、任务包状态和已冻结合同。文中的“建议”“可以”“可能”都保留继续讨论和推翻的空间。

## 1. 这次讨论真正要解决什么

项目需要同时满足两件看似冲突的事：

1. 用户可以导入任意文字世界观和人物设定，而不是只能使用内置 K-pop 样板；
2. 事件结果、数值、位置、日程、关系和其他事实不能交给模型随意决定。

如果只靠代码预写题材分支，系统会不断增加 K-pop、校园、宫廷、末世、奇幻等硬编码，最终无法维护。如果只把整本世界书交给模型自由生成，系统又难以保证条件、权限、事实、结算、重放和存档一致性。

因此当前值得讨论的不是“模型还是代码二选一”，而是两者如何分工，以及任意文字设定如何稳定地变成运行时能够使用的有限信息。

## 2. 当前已经可以确认的事实

### 2.1 当前事件系统以代码驱动为主

现有 Event Runtime 由代码负责：

- 条件与触发来源；
- 随机门槛、冷却和次数限制；
- 选择 ID、结果 ID 和允许的效果；
- Owner Adapter 验证；
- Event Instance、结算和防止重复执行；
- 本地备用文案。

地图开发预览中的 d100、三个结果区间、一次性结算和重开复用均为代码行为。模型不决定这次投掷，也不能增加代码没有声明的选择、结果或数值变化。

### 2.2 AI 文案链路已经存在，但默认关闭且输入很窄

事件文本目前默认使用 `local_only`。用户选择允许的 AI 文案模式后，模型只能在事件已经通过本地条件并正式进入后调用一次；失败时回到本地文案。

现有地图调用传给文本 Composer 的内容主要是：

- 粗略的世界标签、氛围标签和社会秩序摘要；
- 当前地点名称；
- 位置证据来源；
- 当前为空的参与者列表。

它没有完整接入当前启用的世界书内容、用户人设、参与角色档案、关系、所属组织、当日日程或最近事件。因此“支持 AI 文案”目前不等于“模型真正理解当前世界和人物”。

### 2.3 当前世界识别粒度不足以支持任意世界切换

当前 World Context 主要把文字归入：

- `daily`；
- `sci_fi`；
- `apocalypse`。

现代首尔 K-pop、普通都市、校园、古代宫廷和许多奇幻世界都可能落入过于宽泛的 `daily`。现有 K-pop 地图事件兼容检查同样只要求 `daily`，所以粒度不足时存在“世界没有崩溃，但题材事件串台”的风险。

项目还保留了旧的赛博朋克基础世界观默认值。如果用户没有正确启用自己的世界书来源，旧默认文本也可能影响上下文分类。这是需要单独审视的产品迁移问题，不在本讨论稿中预设处理方式。

### 2.4 已有基础可以复用，不必从零重建

项目已经存在一些可继续利用的边界：

- WorldBook 的来源启用、世界文本和百科资料；
- Contacts 的 Self Profile、角色档案模板及具体值；
- Player Context V1 对 `occupation`、`affiliation`、`public_identity` 的只读、版本化投影；
- Event Runtime 的条件、随机、审计、持久化和 Owner Adapter；
- 一次调用、结构校验、本地回退的事件文本 Composer；
- Event Instance 对世界、地点、参与者、来源与结果的稳定引用。

真正缺少的是把这些现有信息组织成“当前事件可以安全使用的世界与人物上下文”的中间层。

## 3. 用户切换完全不同世界观时，可能出现什么问题

### 3.1 不会立刻技术崩溃，但会语义退化

页面、地图、随机数和存档仍可能正常运行，但可能出现：

- 新世界被归入错误或过宽的类别；
- 旧世界专属事件继续出现；
- 事件只能生成泛化内容，无法体现职业、制度和社会关系；
- 新世界没有相配事件时，产品表现为长期无事发生；
- 模型文案提到世界书里不存在的组织、能力或事实；
- 用户以为换了世界，角色、日程或关系仍引用旧世界资料。

这类问题比程序报错更隐蔽，因为界面看起来仍然可用。

### 3.2 世界文本不是动态事实数据库

世界观可以说明“这个世界允许魔法”“行业存在偶像职业”，但不能证明：

- 某角色现在会某个法术；
- 用户今天确实有电视台行程；
- 两个人目前正在交往；
- 某条传闻是真的；
- 某次付款、移动、通话或工作已经完成。

如果不区分“世界允许什么”和“这次实际发生了什么”，模型很容易把背景设定误当成当前事实。

### 3.3 人设可以自由书写，但事件条件需要有限、可审核的信息

用户导入的角色可能使用完全不同的语言描述同一概念。例如“经纪人”“艺人统筹”“负责某团日程的人”可能对应相近职责，但自由文本不能直接授权系统执行组织事件。

需要讨论一种方式，让模型可以提出结构化理解，同时不把模型分类直接升级成事实。用户确认、现有 Owner 证据和版本信息可能是必要组成部分。

### 3.4 世界切换涉及数据边界，不只是换一段提示词

需要区分：

- 全局设置：API、界面偏好、事件频率等；
- 世界范围数据：世界事实、组织、地点语义、世界专属职业与规则；
- 角色范围数据：该角色在某个世界中的身份、关系和经历；
- Owner 事实：日程、位置、通话、订单、付款等真实模块记录；
- 历史事件：已经发生且必须保留原世界引用的结果。

如果这些数据没有明确世界 ID 和版本边界，切换世界后可能污染新世界；如果全部强制隔离，又可能破坏用户希望复用同一角色或通用资料的需求。

## 4. 一个可讨论的混合驱动方向

下面是一种建议，不是既定方案。

### 4.1 世界来源层

继续由 WorldBook 保存用户真正写入或启用的文字：主世界观、世界规则、百科、人物模板和其他来源。长文本仍然是用户可读、可编辑的原始材料。

### 4.2 可审核的“世界运行卡”

世界启用或发生重要修改时，可以从启用来源生成一份有限的运行卡候选，例如：

```text
世界：2026 现代首尔
背景：写实娱乐行业 AU
时代与技术：现代 / 常规科技
地点能力：公司、练习室、电视台、机场、宿舍
行业能力：偶像、经纪、制作、媒体、品牌、粉丝平台
特殊系统：公开身份、舆论、商务、行程压力
事实边界：用户人设优先；现实争议不自动成为事实
```

可能的基本原则：

- 模型可以从自由文本提出候选；
- 用户可以查看和修正关键项；
- 代码保存确认后的有限字段、来源引用和版本；
- 未确认、冲突或低置信内容保持 `unknown`；
- 运行卡描述能力与边界，不成为动态世界事实的万能 Store。

这里是否必须使用模型、哪些字段必须确认、如何避免增加设置负担，都仍需讨论。

### 4.3 通用事件内核与世界事件包分离

通用事件内核可以继续负责条件、随机、冷却、选择、结算、持久化和 Owner 验证。

题材事件不再只声明“适用于 daily”，而可以声明较具体的能力需求，例如：

```text
打歌后台事件
需要：现代娱乐行业 + 电视台地点 + 偶像或工作人员身份
可选：已确认打歌日程
不满足时：不触发，不用模型猜测
```

魔法学院可以有自己的地点、职业和能力标签，但复用相同的事件生命周期、随机、结算和存档机制。

### 4.4 每次事件只组装相关上下文

不建议在每次事件中发送整本世界书。一个事件可以只读取：

- 当前确认的世界运行卡；
- 与事件家族相关的少量世界书片段；
- 当前地点及其 Owner 证据；
- 用户和参与角色的可见、版本化档案字段；
- 与这次事件相关的关系、日程和近期事实引用；
- 代码已经确定的选择、结果范围和禁止事项。

第一阶段可以先依靠明确标签和来源引用。是否需要语义检索、向量索引或更复杂的上下文选择，可以等简单方案无法满足时再决定。

### 4.5 模型写表现，代码守事实

一个可能的分工是：

- 代码先判断事件是否可能发生；
- 模型根据已选事件骨架和限定上下文生成开场、环境、对话和选择文案；
- 代码校验模型只能使用声明过的角色、地点、选择和结果；
- 用户选择后由代码投掷并结算；
- Owner Adapter 决定能否改变对应模块事实；
- 模型失败时仍有本地内容或清楚的无事件路径。

更远期可以讨论让模型提出“候选事件”，但候选不能绕过本地能力匹配、事实验证、权限、随机和 Owner 确认。

## 5. 世界切换可以怎样保持安全

以下是值得验证的建议，并非已冻结流程：

1. 每套世界拥有稳定 `worldId` 和运行卡版本；
2. 切换世界时原子更新“当前活动世界”，不让一半新、一半旧的上下文同时生效；
3. 新事件只读取新世界和与之兼容的角色投影；
4. 已发生事件保留旧世界 ID、版本和来源引用，不因切换而重写；
5. 旧世界的未完成候选可以暂停、失效或等待用户决定，但不能自动移植；
6. 人物是否跨世界复用由明确绑定决定，而不是按姓名猜测；
7. 缺少运行卡或能力不明确时，只开放真正通用的低风险事件；
8. 世界专属事件不兼容时显示可理解的原因，而不是静默串台。

“切换时如何处理正在进行的日程、地点停留和长事件”仍是需要单独讨论的产品问题。

## 6. 建议先做的验证，而不是一次完成全部系统

### 6.1 先做只读的上下文诊断

在不改变事件行为的前提下，能够查看系统当前认为：

- 哪个世界正在生效；
- 使用了哪些 WorldBook 来源和版本；
- 识别了哪些能力；
- 当前用户与参与角色有哪些可用字段；
- 哪些字段缺失、冲突或未确认；
- 某个事件为什么兼容或不兼容。

这可以先证明“系统到底知道什么”，也能避免设置按钮存在但没有真正作用。

### 6.2 用两个差异很大的世界做 A/B 验证

建议用现有“现代首尔 K-pop”和一套最小“魔法学院”测试世界，而不是两个相近都市世界。

可以观察：

- K-pop 专属事件是否只在 K-pop 世界兼容；
- 魔法学院是否不会读取电视台、娱乐公司和粉丝平台能力；
- 同一角色名在不同世界是否保持独立身份；
- 切换回来后原世界事件与结果是否仍然一致；
- 未配置足够资料时是否安全退化，而不是编造。

### 6.3 再连接一个已有事件的 AI 文案

等诊断信息可信后，可以只改造一个地图进入事件：

- 条件与结果保持不变；
- 模型获得确认后的世界、人物、关系、地点和日程摘要；
- 同一地点下，idol、经纪人和普通访客应得到明显不同但事实一致的表现；
- 停用世界来源、角色资料过期或 Provider 失败时，必须回到可解释的本地路径。

这能验证上下文是否真的影响体验，而不需要先建设全部事件类型。

### 6.4 最后才讨论模型提出事件候选

只有当“代码选事件、模型写表现”的链路稳定后，才适合讨论模型根据世界与近期事实提出候选事件。候选事件仍需要结构校验、能力匹配、风险分级、Owner 证据和本地结算。

## 7. 仍然开放的问题

以下问题没有在本次讨论中决定：

1. 世界运行卡由纯代码、模型还是两者共同生成？
2. 哪些字段必须让用户确认，哪些可以自动接受？
3. 用户只想“导入即玩”时，最少需要回答几个问题？
4. 一套世界可以同时启用几个主世界观或能力包？
5. 世界书修改后，已有运行卡是自动失效、生成新草稿还是继续使用旧版本？
6. 同一角色跨世界复用时，哪些资料是全局的，哪些必须分世界？
7. 世界切换时，正在进行的 Journey、Activity、Map place session 和事件如何处理？
8. “通用低风险事件”的范围是什么，怎样避免它们过于无聊？
9. 相关世界书片段先使用标签选择是否足够，何时才需要语义检索？
10. 模型生成文案的成本、隐私、离线体验和缓存策略怎样向用户说明？
11. 用户是否需要一个可见的“本次事件依据”，还是只在 World Hub/诊断模式中查看？
12. 旧赛博朋克默认世界观应该迁移为空状态、保留为示例，还是进入显式世界选择？

## 8. 回家后继续讨论的推荐顺序

为了避免一次讨论所有架构，可以依次回答：

1. 用户导入世界后，愿意确认哪些最少信息？
2. 两个世界之间切换时，用户期待哪些内容继承、哪些完全隔离？
3. 第一条验证事件选择地图进入、Work Hub 工作还是其他场景？
4. 用户希望在哪里看到“系统现在理解的世界和人设”？
5. 确认体验后，再冻结最小运行卡和第一个双世界测试，而不是先冻结万能 Schema。

## 9. 本讨论明确不代表什么

- 不代表已经批准 `World Context V2` 实施；
- 不代表必须新增 Store、World State Ledger、向量数据库或 Event Home；
- 不代表模型可以把自由文本直接变成身份、关系、位置、日程或世界事实；
- 不代表 K-pop 能力标签是其他世界必须遵循的分类体系；
- 不代表世界切换、角色复用或默认世界的产品选择已经确定；
- 不改变当前 Work Hub-first 路线、Player Context V1 边界或 Event Runtime Owner 规则。

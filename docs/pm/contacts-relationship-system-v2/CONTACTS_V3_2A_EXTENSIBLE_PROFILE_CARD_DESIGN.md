## 1. 这一步要解决什么

联系人不应先生成一段“人设文案”，再让其他功能猜这段文字是什么意思。

本阶段建立一种可扩展的人设资料卡：世界观可以提供默认类目，用户可以自己调整类目和字段，也可以粘贴一整段人物描述让系统帮助归类。无论资料来自世界模板、手动填写还是文字归类，确认后都保存为同一种联系人资料，因此 Chat、事件、Work Hub 和后续功能不需要各做一套人物表单。

完整链路：

`世界观内容 -> 建议资料卡 -> 用户增删改并确认 -> 人物填写或整段文字归类 -> 用户复核 -> Contacts 保存统一资料 -> 各功能按用途读取`

## 2. 资料卡的三层结构

### 2.1 系统基础资料

所有世界都需要，但不要求用户填写系统内部编号。

用户可见示例：

- 姓名、称呼、头像；
- 人物类型：我的身份、主要人物、次要人物、世界 NPC；
- 所属世界；
- 一段可选的人物简介。

系统自动管理：

- `profileId`、可见人物编号和绑定引用；
- 人物类型标识；
- 世界、模板和资料版本；
- 创建、修改、归档和恢复信息。

### 2.1.1 人物层级和关系标签必须分开

人物层级回答的是“系统应该让这个人物参与多深”，不是“这个人物和用户是什么关系”。

接受的目标人物类型为：

1. `Self Profile / 我的身份`
   - 用户在当前世界中的自我资料；
   - 不作为聊天对象，也不参加其他人物之间的升级链。
2. `Main Role / 主要角色`
   - 核心人物；
   - 默认可以使用完整聊天连续性、关系成长、记忆和长期剧情能力。
3. `Supporting Role / 次要角色`
   - 会反复出现、拥有稳定资料和持续作用的配角；
   - 可以参与 Chat、事件、组织和轻量记忆，但不默认开启完整攻略或关系成长。
4. `World NPC / 世界 NPC`
   - 世界路人、功能性人物或暂时只被事件、地图、组织引用的人物；
   - 不默认占据主要联系人列表，也不因为被创建就自动进入完整 Chat 或关系系统。

其他人物的自然升级链为：

`World NPC -> Supporting Role -> Main Role`

允许用户按需跨级升级，但升级必须保留同一个人物的稳定 ID、资料值、Chat 绑定和历史、世界与组织引用、事件来源、归档状态和备份内容。降级或归档不能被当成清空历史的快捷方式。

底层代码和存档现已支持 `Self Profile / Main Role / Supporting Role / World NPC` 四类。现有内部 `npc` 值继续作为 `World NPC` 的兼容值；不能通过姓名、聊天次数或模型猜测把旧 NPC 自动改成次要角色。旧人物继续可读，之后由用户明确调整层级。联系人首页暂时仍把 Supporting Role 放在原次级人物列表中，正式四区视觉分组留给后续页面任务。

“家人、朋友、同事、经纪人、同门、敌人”等属于关系标签。一个次要角色可以同时是同事和朋友，一个主要角色也可能是敌人。关系标签可以由世界观扩展并允许多选，但不能代替人物层级，也不能单独授予完整关系成长、Chat 绑定或组织权限。

### 2.2 世界观资料类目

世界观决定“这个世界通常需要了解人物的哪些方面”，而不是直接替人物填写答案。

例如偶像世界可以建议：

- 职业身份：职业、艺名、公开身份；
- 组织归属：公司、组合、队内职务；
- 活动信息：出道日期、擅长领域、公开活动范围；
- 世界设定：特殊规则、身份限制、可公开程度。

仙侠世界则可以改成：

- 出身与种族；
- 门派与师承；
- 修行体系；
- 法器与能力。

### 2.3 人物自定义资料

用户可以在某个模板或某个人物上：

- 新增、删除、改名和排序类目；
- 新增、删除、改名和排序字段；
- 修改填写方式、选项、说明、默认可见范围和用途；
- 把只适合这个人物的字段保留为人物自定义内容；
- 把有复用价值的结构另存为当前世界模板的新版本。

模板更新不能静默覆盖已经确认的人物资料。旧字段要继续保留，并通过差异复核决定是否加入新字段或调整结构。

## 3. 类目和字段不是一回事

类目负责帮助用户理解和浏览，例如“职业身份”“组织归属”。字段才是真正保存和被系统读取的数据，例如“职业”“所属公司”。

每个字段至少需要：

| 用户看到的内容 | 系统需要记住的内容 | 用途 |
| --- | --- | --- |
| 显示名称，例如“职业” | 稳定字段标识，例如 `occupation` | 改名后事件和 Chat 仍能找到同一项资料 |
| 填写方式 | 字段类型 | 决定使用文本框、选择器、日期或人物引用等控件 |
| 可选答案 | 规范化选项值 | 让事件条件不依赖自然语言猜测 |
| 说明 | 帮助文字 | 告诉用户该填什么 |
| 可见范围 | 可见等级 | 控制不同人物或功能可读取的内容 |
| 可以参与哪些功能 | 使用范围 | 在基础人物资料之外，决定是否还能进入 Chat、事件、Work Hub 或公开内容 |

稳定字段标识由系统生成或从受信任的世界模板继承，不要求普通用户填写。用户修改显示名称时，稳定标识不变。

## 4. 建议支持的填写方式

现有系统已经支持短文本、长文本、单选、多选和人物引用。`CARD-2` 已确认首批再开放日期、是/否和组织引用：

- 日期；
- 是/否；
- 组织或团队引用；
- 人物引用；
- 短文本、长文本、单选和多选。

数值、公式和周期计算暂不加入首批类型。动态数值不能因为未来增加了“数值”填写方式就进入联系人。好感度、信任度、疲劳、压力、热度、余额和事件进度仍由各自功能管理；稳定资料应尽量优先用日期、选择项或引用表达。

## 5. 字段怎样服务其他功能

每个字段首先都有基础用途：它是这名人物资料的一部分，可以在联系人中查看、编辑、复核、迁移和备份。不存在“保存下来但完全没有用”的资料。

区别只在于，一项资料是否还适合参加更强的系统行为。每个字段可以在基础人物资料之外，增加一种或多种使用范围：

- Chat 可以读取；
- 事件可以作为触发或判断条件；
- Work Hub 可以用于职业、组织和角色匹配；
- 后续公开页面可以读取公开资料。

这些使用范围不是互斥分类，也不是在判断资料“有没有用”。一项资料可以同时属于人物资料、Chat 上下文和事件条件；也可以目前只作为人物资料，等未来出现明确需求后再增加其他使用范围。

例如：

- 发色、衣着偏好、童年经历：对人物理解和 Chat 很有用，但通常不应授予工作权限；
- 害怕雷声：可以是人物资料，也可以在存在明确雷雨事件规则时参与事件判断；
- 职业：可以帮助 Chat 理解人物，也可以用于事件和 Work Hub 的角色匹配；
- 用户自己的所属公司：可以提供 Work Hub 的组织匹配线索，但仅靠用户填写不能自动开启其工作区权限；
- 其他角色的所属公司与职位：属于已确认的角色设定，不需要角色去 Work Hub 申请或申报；
- 私密备注：对用户自己有用，但可以不提供给 Chat、事件或公开页面。

新建的任意自定义字段默认先成为正常人物资料，不会因为系统暂时不知道它的确切含义，就自动获得事件判断、工作匹配或公开权限。用户或世界模板之后可以为它补充明确的使用范围。

这些使用范围只是“允许被读取或匹配”，不代表字段值可以自动产生结果或授予权限。

`CARD-2` 使用四个稳定用途标记：`chat_context`、`event_eligibility`、`work_hub_matching`、`public_content`。基础人物资料价值是所有字段天然具有的能力，因此不需要额外标记。旧字段升级后用途为空；长文本不会进入精确事件判断或 Work Hub 匹配，日期和是/否不会直接承担 Work Hub 角色/组织匹配。后续消费者还必须同时检查人物类型、资料可见范围、世界和模板版本，不能只看用途标记。

### 5.1 用户和其他角色的组织资料不对称

这条限制主要约束用户自己的 Self Profile，不能机械套用到所有人物。

- Self Profile：用户填写“所属公司、学校、团队”可以建立人物身份和匹配目标，但是否进入用户自己的 Work Hub、能处理哪些内部工作，需要用户侧的组织关系或工作区确认；
- Main Role、Supporting Role 和 World NPC：所属公司、学校、门派、组合、职位等可以直接作为其稳定角色资料保存，不要求这些角色逐个打开 Work Hub、提交申请或完成入职；
- Work Hub 可以按稳定人物 ID 引用相关同事、负责人、艺人、老师或学生，不需要复制一份人物资料；
- 当某个角色代表组织向用户发送正式工作通知、日程变更或批准结果时，需要确认的是“这条组织记录和发送来源有效”，不是要求该角色本人拥有一个面向用户的 Work Hub 账户；
- 普通人物互动、Chat 上下文和身份条件事件可以读取已确认的角色资料，不必等待 Work Hub 建档。

因此，Contacts 负责“这个角色是谁、属于哪里、担任什么身份”；Work Hub 主要负责“用户在该组织里能做什么，以及组织向用户发出了什么正式工作记录”。

例如：

`用户职业=签约艺人 + 用户所属公司=A 公司`

可以让系统选择 A 公司作为用户 Work Hub 的匹配目标，但正式的“公司发来打歌通知”仍需要一条有效的组织工作记录。对于其他角色，`职业=签约艺人 + 所属公司=A 公司` 本身可以作为已确认角色身份供 Chat 和普通身份条件事件读取，不要求该角色先去 Work Hub 申报。事件成立后产生的好感变化、工作任务、日历安排和日记记录，仍分别交给关系系统、Work Hub、Calendar 和记录功能保存。联系人不会保存这些动态结果。

自定义字段也应沿用这套逻辑：它拥有稳定标识、明确填写方式和用途后，就能通过统一资料读取规则被使用，而不是退化成只能展示的一段备注。

## 6. 整段文字归类的工作方式

用户可以粘贴类似下面的内容：

> 我叫林夏，是星河娱乐的签约艺人，在组合 Aurora 中担任队长，公开艺名是 Livia，私下不喜欢别人叫全名。

系统只生成待复核结果：

- 姓名：林夏；
- 职业：签约艺人；
- 所属公司：星河娱乐；
- 所属组合：Aurora；
- 队内职务：队长；
- 公开艺名：Livia；
- 称呼偏好：不喜欢别人叫全名。

归类规则：

1. 优先放入当前资料卡已有字段；
2. 找不到合适位置时，建议新增字段或放入“待归类内容”；
3. 同一段文字出现冲突时，同时展示冲突内容，不擅自选择；
4. 已有用户确认值不会被新文字静默覆盖；
5. AI 或规则归类只是草稿，用户确认后才写入联系人；
6. 取消、解析失败或保存失败时，原人物资料保持不变。

整段文字不是联系人中的第二套人物格式。它只是填写统一资料卡的一种便捷入口。

## 7. 个人页面上的表现

联系人点进某个人后，个人详情页本身就应呈现这张可扩展资料卡，而不是把世界观字段和自定义字段长期藏在一个独立的“其他信息”或“世界字段”列表中。

页面按信息深度分为四层：

### 7.1 人物概览

进入页面后直接看到：

- 头像、姓名、称呼和人物类型；
- 当前世界和主要身份摘要；
- Chat、编辑资料等主要操作；
- 需要复核的模板变化或文字归类提示。

这一层只回答“这是谁、目前是什么状态”，不塞入完整表单。

### 7.2 可扩展资料区块

人物概览下方按当前资料卡类目动态生成区块，例如：

```text
人物概览

职业身份
  签约艺人 · 队长 · 艺名 Livia

组织归属
  星河娱乐 · Aurora

称呼与相处
  不喜欢别人叫全名

世界特殊设定
  添加资料

+ 添加资料类目
```

表现规则：

1. 世界模板新增一个类目后，使用该模板的人物页可以出现对应的新区块和“待补充”提示；
2. 用户为某个人新增类目后，该类目只出现在这个人物的资料卡中，除非用户主动选择“加入当前世界模板”；
3. 查看状态优先显示已经填写的重点内容，不把几十个空输入框一次性铺满页面；
4. 未填写的必填或推荐字段使用自然语言提示，例如“建议补充所属组织”，不把人物资料表现成 `3/4` 一类任务完成度；进入编辑状态后再显示具体空字段；
5. 类目顺序来自模板，但用户可以调整；收起或展开状态只影响页面浏览，不改变资料本身；
6. 每个类目使用一致的点击行为：点击区块进入该类目的查看或编辑，不让不同类目分别跳向无关页面。

### 7.3 类目内表单

进入某个类目后，才显示该类目完整字段和对应填写控件。用户可以：

- 修改已有值；
- 增加一个字段；
- 调整字段顺序和可见范围；
- 查看某字段可供 Chat、事件或 Work Hub 使用的说明；
- 选择新字段“只给这个人物”或“加入当前世界模板”；
- 保存或取消本次修改。

普通填写时不要求用户理解稳定字段标识、资料版本或内部绑定 ID。这些内容只在高级管理或诊断信息中出现。

### 7.4 辅助填写动作

“从一段描述补充资料”属于帮助用户完成表单的操作，不是另一个资料页。

它可以从人物概览或编辑入口打开，完成后必须回到同一张资料卡进行复核：

- 已匹配内容按类目分组显示；
- 新字段建议明确标出；
- 冲突和无法归类的原文单独保留；
- 用户可以逐项接受、修改或忽略；
- 最终保存后，结果出现在相应资料区块中。

### 7.5 查看状态与编辑状态

个人页不应永远保持“大表单”外观。

- 查看状态是一张容易浏览的人物资料卡：按类目显示摘要和已填写内容；
- 编辑状态才是可扩展表单：展示完整字段、空项、控件和新增操作；
- 管理世界模板属于 WorldBook；个人页只管理这个人物的具体值和人物专属扩展；
- 当用户希望把人物专属结构复用给其他人物时，再明确引导其保存为当前世界模板的新版本。

## 8. 与现有系统资料卡怎样兼容

现有联系人已经使用：

- `profileTemplateId` 和模板版本记录人物套用的模板；
- `profileValues` 按稳定字段 ID 保存具体值；
- 字段可见等级；
- 模板变更后的差异复核和旧字段保留；
- 已支持 Self Profile、Main Role、Supporting Role、NPC 的统一人物类型逻辑。

V3-2A 不另造一套人物存档。建议采用兼容扩展：

1. 在现有模板上增加类目分组、用途标记和后续字段类型；
2. 没有类目信息的旧模板自动显示在一个默认类目中；
3. 旧 `profileValues` 继续按字段 ID 读取，不要求一次性迁移；
4. 用户新增的类目和字段仍生成正常模板字段或人物自定义字段；
5. 所有确认结果继续通过 Contacts Profile Owner 保存并产生人物资料新版本；
6. Chat、事件和 Work Hub 后续只读取经过筛选的资料结果，不直接读取整张资料卡。
7. Supporting Role 作为正式人物类型加入同一套模板和值结构；现有 `npc` 继续表示 World NPC，旧记录不自动改类。
8. 人物专属结构保存在人物档案的 `profileExtensions` 中，读取时与世界模板合并，保存时仍保持人物和模板各自归属；旧人物自动得到空扩展，不需要迁移存档版本。

这样能保留当前系统资料卡逻辑，同时让它从“固定字段列表”成长为“世界可调、用户可改、系统可读”的资料卡。

当前 `ContactsView` 已把原有世界字段区块扩展为按类目生成的人物资料卡：默认阅读状态只显示已填写内容和自然语言补充提示，明确进入编辑后才显示完整表单。旧平面模板进入默认资料类目，人物原有补充字段继续保留；没有并排增加另一套“新版人设页”。用户可从同一编辑页添加人物专属类目/字段，并明确选择只保存给这个人物，或在正式保存时把结构加入当前世界模板。WorldBook 规则/可选 AI 模板草稿和整段人物描述归类都进入现有复核流程；取消不落库。Persona Confirmation 要求逐项接受或忽略，保存前重核版本，并通过 Contacts Profile Owner 一次写入同一资料结构。正式 Chat、Event Player Context 和 Work Hub 只读取获准用途的精简字段；后续生命周期和公开页面投影不属于本设计阶段。

## 9. V3-2A 的实施边界

这一阶段先完成“资料卡结构设计和模板草稿复核”，不同时完成所有下游功能。

应完成：

- 类目、字段、填写方式、可见范围和用途的规则；
- 世界观生成建议资料卡；
- 用户增删改、排序和确认；
- 旧模板与旧人物资料的兼容方案；
- 整段文字归类所需的候选结果格式。

暂不完成：

- 自动修改已确认人物；
- 自动授予工作身份、组织权限或事件资格；
- 把好感、疲劳、余额等动态数据放入联系人；
- 正式迁移 Chat、事件或 Work Hub；
- 资料卡页面的全面美化。

## 10. 第一阶段验收标准

1. 用户能看懂“类目”和“具体字段”的区别；
2. 不同世界可以生成不同资料卡建议；
3. 用户可以自由调整建议，并保留人物专属内容；
4. 整段文字可以被拆成可复核字段，未识别内容不会丢失；
5. 所有确认结果继续保存为现有联系人资料，而不是第二套人设文案；
6. 自定义字段具备稳定标识、填写方式和用途，不会只能展示；
7. 旧模板、旧人物值、人物 ID、Chat 绑定和备份格式保持可读；
8. 任何自动建议都不能绕过用户确认；
9. 动态数据继续由关系、事件、工作、日历、账本等原有功能管理。
10. 点进任意人物后，用户能在同一个个人页看到按类目生成的资料区块，并从相同位置进入对应表单编辑；新增类目不需要另做一张页面。

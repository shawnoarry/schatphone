# Chat And Chat Directory Package

Updated: 2026-08-10

Use this package for Chat thread behavior, Chat Directory, service accounts, role binding into Chat, and message-surface work.

Confirmed persistence boundary: user-visible Chat history and saved messages require explicit user deletion. Older records may be paged or moved into reversible cold archives, but capacity management must preserve review/restore behavior and cannot redefine Contacts lifecycle or Relationship Runtime truth ownership.

Confirmed AI-artifact boundary: Chat persists messages and rich content formally committed to Chat plus the minimum provenance needed for the thread. It does not persist complete assembled prompts, raw provider responses, uncommitted candidates, or transport payloads by default; full capture belongs only to explicit temporary diagnostics. Future social, forum, offline, narrative, performance, or character-state modules persist their own committed canonical content rather than routing it through Chat.

Current role-activation boundary: Contacts may expose an explicit `Start Chat` action for an eligible Main Role or NPC, but it calls the existing Chat-owned idempotent binding seam and routes only from the returned contact. Chat Directory remains the management surface for bound targets, unbind, and Chat-local metadata. Self Profile is never a Chat target, and Book text, encyclopedia selection, and extra World Packs remain optional.

Current role-payee boundary: role profiles own stable fictional receiving-account definitions. Chat may request and render one only as a system-generated `payee_account` share card built from the persisted profile; the AI must not invent or output bank credentials. The request and account card do not move money. Wallet owns the disclosed reference, confirmation, same-currency validation, ledger mutation, receipt, and resulting relationship fact.

Current Wallet receipt-share boundary: Wallet may prepare a completed role-transfer receipt as `wallet_receipt_share`, but Chat still owns recipient selection, explicit send, message history, and the receiving-conversation return context. Chat attaches `returnChatId` only when the card is finally sent. Opening the card returns from Wallet to that receiving conversation without replacing the transaction's original Chat lineage or mutating money state.

Together they own active chat selection, active conversation/messages, merged AI prefs, communication availability, Chat appearance classes, avatar/module identity read models, in-flight AI request state, system-prompt/context preparation, image-reference metadata/context/role-bound/Gallery preparation, assistant JSON/reply/rich-block normalization, assistant reply notification/social-event/read-state/truth-count post-processing, automation status copy, Messages search/list grouping, folded-service unread totals, service-thread muted/folded flags, service status/source-plan/empty-state copy, composer-adjacent source/reply/read/sent feedback display, edit-modal field/validation state, message action-sheet rows/labels/visibility, `+` panel form/draft/gallery-readiness state, thread-menu open/draft/save-feedback payload state, and pending quote bar/payload cleanup state without changing Chat schema, service notification behavior, AI transport, assistant parsing semantics, automation scheduling, routing, storage, message mutation actions, Wallet writes, Gallery asset binding, media import, Shopping share semantics, or visible UI.

Current 4.4 note: Shopping, Logistics, and Food Delivery can now push reusable Chat service-notification messages with source references and route actions. Chat owns the message history; the source modules keep the business records. Chat-side source notification plans now describe which source modules can push event-driven updates into a joined service account; these plans are descriptive and do not auto-create subscriptions or source records.

Current subscription UX note: service and official accounts now behave more like chat-app subscription channels. Folded subscriptions stay out of Messages but have a visible folded-subscriptions entry back to Services, service threads expose channel status plus mute/fold controls, and Services presents accounts as grouped feed sections (`Unread updates`, `Today`, `Earlier`, `No updates yet`). The folded entry and Services summary now distinguish folded unread, muted unread, and all-read states, so users can tell messages were quietly kept rather than lost. Services also has inbox-style filter explanations, count chips, selected summary cards, and contextual empty states, so users can understand no-unread, muted, folded, search, service-only, and official-only states without reading backend-like terms. When users open a service thread from Services, Chat preserves the source filter on return, highlights the selected service when it is still visible, scrolls it back into view, and shows a recovery panel if the account left the current unread filter because the thread was read. Users can clear unread subscription updates one account at a time or all at once without opening every thread; mark-read feedback explicitly says notification cards stay in the thread. Service threads add date dividers plus a lightweight digest before consecutive notification runs, so repeated pushes read like a message timeline instead of a backend feed. Same-day follow-up pushes from the same service source now use compact cards after the first full card, keeping source-open and Chat reply actions available while making a dense thread readable on one phone screen. Empty service threads now show a subscription-home empty state rather than a blank backend-like surface. Service threads now also show an account-like channel card with the service name, source chips, replyability, source-ownership boundary, history-retention promise, and current inbox placement. Service-notification cards show user-facing source labels instead of backend module keys and separate source-detail actions from Chat reply actions, explaining that source actions open details while replies stay in Chat. Notification cards now also use source-specific presentation for Shopping orders, logistics tracking, and Food Delivery updates so the timeline reads like real chat-app service messages instead of one generic backend feed. Opening a service notification is still a normal chat-thread experience: users can quote/reply to the notification inside Chat while the source module keeps the business record; when users return from a source detail, Chat shows source-open status near the composer, offers an open-again action, and states that Chat did not mutate source-module business state. Service notification reply and sent states also appear near the composer, and opening an unread service thread confirms that Chat only cleared the unread counter while keeping notification cards and source records intact. The composer status, quote bar, errors, and notices now live in normal bottom layout flow rather than overlaying message cards, which reduces mobile action-button overlap. Service-account AI replies receive the service template plus notification context and are instructed to answer conversationally without claiming to mutate source-module business state.

Current WorldBook note: Chat prompt assembly and the thread WorldBook summary now consume the same `world-interface` result, so the user-visible active knowledge state matches the world context sent to AI.

Current/future Mini Scene note: today's Chat `mini_scene` rich block is Chat history with an inert `htmlSnippet` code preview, not the shared interactive popup system. Under roadmap 4.8, new Chat-triggered scenes will later call the shared Mini Scene Interface, retain Chat source truth, and store only an artifact reference plus display snapshot where needed. Legacy snippets must never be executed or silently migrated to HTML.

Optional capability Pack note: enabled World Pack service-account templates are surfaced as availability only, while the actual opt-in lives in Chat Directory's `Services` management area. Users can join service/official account candidates from every enabled compatible expansion pack; Chat Directory shows the source pack per candidate, creates or reuses the generated account through the idempotent World Pack service-template seam, records only origin metadata, and keeps WorldBook out of service-account editing/creation. Chat exposes `getServiceAccountLinkContract(contactId)` so follow-up source-module work can inspect the Chat-owned thread route, source bindings, source notification plan, required `service_notification` fields, interaction capabilities, and source-record boundary without reading Chat UI internals.

Optional capability Pack service-template edit note: built-in enabled-pack service/official account candidates can now be edited and reset inside Chat Directory's `Services` management area before the user joins them. The editable fields are user-facing account name, account kind, description, and linked world-app binding; user overrides are stored on that candidate's source World Pack template metadata and marked as customized, while joined Chat accounts remain Chat-owned subscription entries and are not silently overwritten by later template edits. AI-suggested service candidates now enter through the same Chat Services review lane: AI or pasted JSON can propose service/official account templates from active WorldBook/World Pack context, low-confidence/duplicate/unknown-binding proposals are rejected, and confirmed proposals only become World Pack templates until the user manually joins them.

Current Chat App shell note: Chat now presents a messaging-app style product shell with first-level tabs for `Messages`, `Contacts`, `Groups`, `Services`, and `Me`. Messages stays the immersive conversation home; Chat contacts, group management, and service accounts have their own first-level tabs. `Contacts` is a conversation-first list: opening a row enters the chat, state-dependent social actions stay primary, and Chat-local preferences plus unbind remain under one secondary action menu. `Me` is the Chat identity/anonymity, saved normal-chat messages, recent interaction data, and derived social-data page, while the top-right gear opens Chat Settings for Chat Appearance, default-behavior entry points, and maintenance diagnostics. The release-facing thread UI keeps the Messages home free of a permanent explanation card, uses a contact-first bottom sheet for chat details, collapses WorldBook/avatar/reply/automation controls, and keeps the `+` panel as a compact launcher. Ordinary assistant-message actions are quote, copy, save, regenerate, and delete; editing and forced contact recall are not ordinary immersive actions. User-authored role/group messages still distinguish delete from recall, and user-authored rich message edits keep structured UI, copy, and AI context aligned. Shopping selection stays in Shopping and returns source-owned `share_card` objects; the Chat composer does not embed a product catalog or claim checkout/product truth. `Me` intentionally excludes service-account feed semantics until the World Pack service-account direction settles.

Current Chat appearance note: `systemStore.settings.appearance.chat` persists the layout class plus independent message avatar, bubble-shape, theme-color, and bubble-color modes. `messageAvatarMode` accepts `layout`, `all`, or `hidden`; `messageBubbleMode` accepts `bubble` (follow style), `soft`, `outline`, or `glass`, and invalid legacy/backup values, including the retired `plain` value, fall back to the visible `bubble` default. `themeColorMode` accepts `layout`, `ocean`, `mint`, or `coral`; `bubbleColorMode` accepts `theme`, `contrast`, `soft`, or `mono`, and missing/unknown values fall back to `layout` and `theme`. One shared class resolver now applies the selected layout and theme to every Chat-owned route shell: Messages and threads, Contacts/Services, Groups, Me, Chat Settings, Chat Appearance, and retained feature pages. Theme color styles page backgrounds, headers, sheets, panels, tab bars, composer, primary actions, and home accents, while bubble color independently sets contact/user bubble contrast. The Kakao-like layout keeps an incoming contact identity anchor while leaving the user side lighter, matching the product's current Kakao reference rather than treating it as an iMessage clone. The iMessage-like layout makes message rows avatarless by default and adds a centered circular contact avatar, name, and Chat-local note/status in the thread header; blue user bubbles and neutral contact bubbles remain presentation choices only. The appearance page now places a shared live header/thread/composer preview before its controls, keeps the preview in the first screen, and uses compact layout/theme/bubble selectors with one selected-option detail line instead of repeated tall cards. Chat custom CSS remains Chat-owned and can be stored as named local profiles under the appearance settings, with the legacy `customCss` field retained for compatibility.

Current group-chat note: group chats are first-class Chat targets backed by Chat-side role member ids and a group reply mode. V1 stores and surfaces the group target cleanly; deeper multi-speaker orchestration remains a future behavior layer.

Current relationship-compatibility note: Chat Directory still preserves legacy `relationshipLevel` and `relationshipNote` fields for binding compatibility, but the UI labels them as Chat-local tuning/note only. Current relationship truth stays in relationship runtime.

Incoming social-event note: Chat social/channel state has a V1 applied shell for direct user actions such as greetings, request acceptance/decline, blocking, unblocking, and blocked-by-role markers. Generated role-initiated social events now enter the explicit review seam: Chat owns messaging accessibility and visible social-channel state, Contacts displays the role-level snapshot only, Event Runtime owns eligibility/review/audit, World Hub reviews high-risk proposals, and relationship runtime receives only confirmed relationship facts or memories.

Current Chat preview note: the default Kakao, WeChat, and iMessage layouts each carry an explicit shell/thread palette. Chat Appearance previews label contact versus user messages, show the iMessage header identity row, and explain that letter avatars are replaceable placeholders.

Current Chat sizing note: ordinary text bubbles use content-fit sizing for short messages and a bounded, wrapping width for long messages; rich cards, images, and service notifications keep the available message-column width.

Current TTS note: Chat Settings exposes `/chat-settings/voice` as the configuration and temporary preview surface for the shared runtime TTS Module. Cloudflare MeloTTS is the development default and MiniMax is the user-key Chinese validation path. Chat does not own the provider transport or preview audio, and the first slice does not change `voice_virtual`, persist generated audio, or speak replies automatically.

Current composer note: the active thread uses a bounded auto-growing multiline composer. `Enter` sends, `Shift+Enter` inserts a line break, IME composition is not treated as send, and drafts keep their line breaks across the existing Network setup return flow. While an AI reply or regeneration is running, the reply trigger becomes an in-context stop action; intentional cancellation is normalized to user-facing copy and keeps the existing retry target.

Current internal-App collaboration note: `push`, `share`, `quote`, and `open source` are separate behaviors. Source-owned commerce events enter joined service threads as `service_notification`; a user-initiated Map place, Music track, or Wallet receipt share becomes one normalized `share_card` only after choosing a conversation and confirming send; quoting stays inside Chat; opening the card restores the exact source detail without changing trip, playback, payment, or other source state. Wallet receipt finalization additionally binds the receiving conversation so Wallet returns there rather than to the transaction's original Chat lineage. One 24-hour device-local draft supports cancel-to-source and refresh/lock recovery, is excluded from backup, and is cleared after send or cancel. Desktop and simulated Pixel 5 Playwright cover the current flows. No OS/PWA share target is claimed.

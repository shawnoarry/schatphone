# Chat And Chat Directory Status And Handoff

Updated: 2026-08-09

This file is the handoff page for Chat, Chat Directory, service accounts, and Chat-side role binding work.

## 1. Current Status

Status: `PARTIAL_DONE`

Confirmed persistence dependency for future work:

- ordinary and archived role threads, user-visible message history, and saved messages cannot be silently or irreversibly deleted for capacity management;
- older messages may be paged or moved into reversible cold archives, but Chat must preserve review, search/restore expectations, source references, and paused-thread read-only semantics;
- Chat owns conversation behavior and records only; it does not own global role lifecycle or relationship truth.
- Chat durably stores messages/rich records formally committed to Chat and minimum AI provenance, not the full assembled prompt, raw provider response, uncommitted candidate, or transport payload; future modules own their own committed content, and any full capture is an explicit temporary diagnostic concern.

What is already landed:

1. Chat is a mature core lane with threads, rich messages, AI reply flow, and thread-level preferences;
2. Chat Directory and Contacts now have a clearer product boundary;
3. role binding into Chat is treated as a Chat-side entry concern, not a replacement for the global role archive;
4. service-account style messaging now connects Shopping checkout, Shopping logistics events, Food Delivery checkout, and Food Delivery order events into Chat through reusable notification messages.
5. Chat role-binding contracts now carry Contacts entity type, WorldBook template links, profile values, and capability flags.
6. Chat prompt context now orders primary worldview rules before current role profile values, visible user self-profile values, relationship runtime context, and supplemental role-bound knowledge points.
7. service notifications store source module/id references, optional source event id, status, amount, service label, and route actions while avoiding copied business state.
8. Chat prompt assembly and the thread WorldBook summary now consume the same `world-interface` context, so enabled/disabled/missing role-bound knowledge counts match what is sent to AI.
9. enabled World Pack service-account templates are currently presented in WorldBook as availability only, while Chat Directory's `Services` management area owns the user opt-in list. Users can join service/official account candidates from every enabled compatible expansion pack in Chat, and each row shows its source pack. Before joining, users can edit the built-in candidate's account name, account kind, description, and linked world-app binding, save the candidate as a customized World Pack template override on that source pack, or reset it back to the built-in version. Chat Services can also review AI/pasted service-candidate proposals against the active WorldBook/World Pack context; confirmed proposals become World Pack templates only, and still require a separate user join action. Template rows and joined service threads now show a Chat-side source notification plan: available candidates say which source-module event streams will become ready after join, while joined accounts expose the ready plan through the linkage contract. The generated account carries origin metadata (`worldPackId`, `worldServiceTemplateId`, `worldAppBindingId`) and duplicate prevention while staying a Chat-owned subscription entry, and later template edits do not silently overwrite already joined accounts.
10. Chat App now has a first-level messaging-app shell: `Messages`, `Contacts`, `Groups`, `Services`, and `Me`, with the old thread-list status decoration removed in favor of search/new-chat/settings controls. `Contacts` opens a chat from the row, keeps one state-specific social action primary, and groups Chat preferences, block, and unbind under a single secondary menu; it remains a Chat-side binding surface rather than the global role archive. `Me` is scoped to Chat identity/anonymity, recent interaction data, and lightweight derived feed items; it should not become a duplicate contact/group/service shortcut hub. The current visual polish adds a more Kakao-like Messages header/list sheet, active bottom-tab treatment, and `Me` compact stats plus a recent-interaction avatar rail without changing the underlying conversation or identity data model.
11. the top-right gear now opens dedicated Chat Settings. Chat Settings owns Chat Appearance, default-behavior entry points, and maintenance diagnostics; the old `/chat-feature/more`, `/chat-feature/identity`, and `/chat-feature/labs` routes redirect to the new owners.

Chat Appearance V1 is persisted under `systemStore.settings.appearance.chat`, defaults to the Kakao-like immersive preset, supports WeChat/Kakao/iMessage layout classes, independent `messageAvatarMode` values (`layout`, `all`, `hidden`), independent `messageBubbleMode` values (`bubble`, `soft`, `outline`, `glass`), independent `themeColorMode` values (`layout`, `ocean`, `mint`, `coral`), and independent `bubbleColorMode` values (`theme`, `contrast`, `soft`, `mono`), and injects Chat-specific custom CSS separately from global Appearance CSS. The existing `bubble` value means follow the selected layout and remains the visible fallback for invalid legacy or backup values, including the retired `plain` value; missing or unknown color values fall back to the layout theme and theme-following bubble palette. The appearance page now leads with the shared live header/thread/composer preview, keeps it inside the first screen, and uses compact layout/theme/bubble selectors with one selected-option detail line. A shared shell-class resolver carries the selected layout and theme through Messages/threads, Contacts/Services, Groups, Me, Chat Settings, Chat Appearance, and retained feature routes. Theme color styles page backgrounds, headers, sheets, panels, tab bars, composer, primary actions, and home accents; bubble color independently sets contact/user bubble contrast. Named Chat CSS profiles can be saved locally, selected later, updated, saved as a new profile, cleared, or deleted; legacy `customCss` is migrated into a `Custom CSS` profile when needed. Kakao-like rows keep an incoming contact identity anchor while the user side stays lighter; iMessage-like rows hide message avatars by default but add a centered circular contact avatar, name, and Chat-local note/status to the thread header, with blue user and neutral contact bubbles.

14. Chat Directory now labels legacy `relationshipLevel` and `relationshipNote` as Chat-local tuning/note fields, with copy that says they are not current relationship truth.
15. service and official accounts now have subscription-channel controls in the thread, a folded-subscriptions entry from Messages back to Services, and user-facing service-notification cards that avoid backend source labels. Service notification cards can be quoted/replied to as normal Chat messages, so service threads are not read-only subscription posts. Service threads now add date dividers, a lightweight digest before consecutive notification runs, compact follow-up cards for same-day same-source pushes, a subscription-home empty state, and a Chat-side source-open reminder when users return from source details; each notification card stays visible and replyable. Service threads also show an account-like channel card with the service name, source chips, replyability, source-record ownership, history-retention promise, and current inbox placement so the thread reads like a chat account rather than a backend feed. Notification cards now explain that source actions open details while replies stay in Chat; source-detail actions and Chat reply actions are visually separated, and Shopping order, logistics tracking, and Food Delivery notifications each have source-specific tone, icon, action copy, and ownership copy without copying source-module business records. Reply actions show a Chat-side context-ready state, source-open feedback offers open-again, sent-reply feedback confirms the reply stayed in Chat, and read feedback says cards stay in the service thread. The Services inbox layer now adds filter count chips, selected summary cards, filter-specific explanations, and recovery-oriented empty states for first-use, no-unread, muted, folded, service-only, official-only, search, and service-thread-return cases. The Messages folded-subscriptions entry and Services account rows now distinguish folded unread, muted unread, and all-read states, making it clear that quiet or folded updates are retained in Services. The composer status, quote bar, errors, and notices now use normal bottom layout flow instead of floating over message cards, reducing overlap with service-notification buttons on phones. Service-account AI replies now receive explicit service-channel instructions and notification context, while Chat still does not claim to change source-module business records.

## 3. Do Not Do

1. Do not let Chat Directory turn into the global role archive.
2. Do not move destructive role cleanup into Chat or Chat Directory.
3. Do not mix service accounts into role-profile logic without an explicit contract.
4. Do not present `relationshipLevel` or `relationshipNote` as the current relationship truth.
5. Do not treat Chat Directory membership as proof that a Contacts entity is a Main Role.
6. Do not bind Self Profile as a Chat target.
7. Do not let group chat membership create, delete, or rewrite global Contacts role records.
8. Do not reintroduce bulk thread tuning as the main `Me` or Chat Settings experience.
9. Do not put appearance, diagnostics, or default conversation settings back into the bottom `Me` tab.
10. Do not let Chat-side friend/block state become current relationship metrics, stage, or memory truth.
11. Do not let AI-generated or runtime-generated role social proposals mutate Chat state directly; they must go through the event-runtime social-event review seam.
12. Do not make Chat own currency definitions, exchange rates, transfer confirmation, receipts, or a separate ledger; Wallet owns those records, and Chat account cards must not deduct funds.
13. Do not execute legacy `htmlSnippet`, accept raw generated HTML, or copy Mini Scene profile/regex/presenter logic into Chat.

Current Chat preview note: the default Kakao, WeChat, and iMessage layouts each carry an explicit shell/thread palette. Chat Appearance previews label contact versus user messages, show the iMessage header identity row, and explain that letter avatars are replaceable placeholders.

Current Chat sizing note: ordinary text rows shrink the bubble to content for short messages, cap long text at the message-column width with wrapping, and keep rich cards, images, and service notifications on a full available-width treatment.
